# MTA Daily Ridership Analysis

Week 1 project for the MTA Daily Ridership dataset. The pipeline cleans and
validates the daily MTA data, models it as a small star schema, exports the
dimension and fact tables to CSV, and loads them into PostgreSQL.

## Project structure

```text
MTA Project/
├── README.md
├── .gitignore
└── WEEK ONE/
    ├── MTA_Daily_Ridership_Cleaned.csv     # generated by the notebook
    ├── data/
    │   └── raw/
    │       └── MTA_Daily_Ridership.csv     # immutable source copy
    ├── database/
    │   ├── dim_date.csv                    # generated by the notebook
    │   ├── dim_transportation.csv          # generated by the notebook
    │   └── fact_daily_metrics.csv          # generated by the notebook
    ├── python/
    │   └── MTA_Processing.ipynb            # cleaning, EDA, schema export
    └── sql/
        ├── tables and relationships.sql    # schema (rebuilds empty tables)
        └── load.sql                        # CSV load + post-load checks
```

`data/raw/MTA_Daily_Ridership.csv` is the original export and must not be
edited. `MTA_Daily_Ridership_Cleaned.csv` and the three files in `database/`
are reproducible outputs; regenerating them with the notebook should not change
their values.

## Dataset

- Source: MTA Daily Ridership (daily ridership, scheduled trips, and traffic).
- Coverage: 2020-03-01 through 2024-10-31, 1,706 consecutive calendar days.
- Source table: 1,706 rows × 15 columns (date + 7 activity measures + 7
  comparable pre-pandemic percentages).
- Data quality: no missing values, no duplicate rows, no duplicate dates, and
  no negative values in the source data.
- The bundled raw copy and the cleaned output are byte-identical
  (SHA-256 `6e3ff89e6cb35a0fda4c668b86f4388c2b111d446b42d7f745c00ef60c644dbf`),
  because this dataset required validation and reshaping rather than value
  correction.

## Star schema

| Table | Grain | Rows | Key |
| --- | --- | ---: | --- |
| `dim_date` | One row per calendar date | 1,706 | `date_key` (PK) |
| `dim_transportation` | One row per transport system | 7 | `transport_id` (PK) |
| `fact_daily_metrics` | One row per date × transport system | 11,942 | `(date_key, transport_id)` (PK) |

`fact_daily_metrics` has foreign keys to both dimensions. Both foreign keys and
all dimension attributes are `NOT NULL`; `activity_value` and
`recovery_percentage` have non-negative `CHECK` constraints. Foreign-key
columns are indexed. The fact grain is exactly 1,706 dates × 7 systems =
11,942 rows, with no duplicate `(date_key, transport_id)` pairs.

The dimensions are intentionally small:

- `dim_date`: `date_key`, `year`, `month`, `day`, `day_name`.
- `dim_transportation`: `transport_id`, `transport_name`, `activity_measure`.
- `fact_daily_metrics`: `date_key`, `activity_value`, `recovery_percentage`,
  `transport_id`.

## Activity measures are not one unit

`activity_value` is stored in one column, but its unit depends on the transport
system:

| Transport system | `activity_measure` | Unit |
| --- | --- | --- |
| Subways | Estimated Ridership | Estimated riders |
| Buses | Estimated Ridership | Estimated riders |
| LIRR | Estimated Ridership | Estimated riders |
| Metro-North | Estimated Ridership | Estimated riders |
| Access-A-Ride | Scheduled Trips | Scheduled trips |
| Bridges and Tunnels | Traffic | Vehicles |
| Staten Island Railway | Estimated Ridership | Estimated riders |

Do not sum `activity_value` across all seven systems: that would add riders,
scheduled trips, and vehicles together. Compare systems within the same measure,
or aggregate only systems that share a unit and state that choice explicitly.

## What `recovery_percentage` means

`recovery_percentage` is the source dataset's
`% of Comparable Pre-Pandemic Day`. It compares a day's activity with the 2019
average for the same month and day type (weekday/weekend), not with the total
activity of all systems. A value of 100 means activity matched the comparable
2019 baseline; values above 100 are above that baseline.

Source caveats that affect interpretation:

- LIRR and Metro-North values are modeled estimates.
- Bridges and Tunnels traffic is preliminary.
- Access-A-Ride reports scheduled trips, not completed trips.
- Recent days may be revised in later source releases.
- The source documentation says LIRR/Metro-North start on 2020-04-01, while the
  CSV contains March 2020 values; the CSV values are retained as published.
- The documentation's wording about subways including Staten Island Railway
  conflicts with the CSV, which has a separate Staten Island Railway column.
- The source methodology changed in February 2023.
- Percentages are whole numbers, so very small activity relative to the 2019
  baseline can round to 0.

### Staten Island Railway zero values

Staten Island Railway has 32 rows with `activity_value = 0`, all on weekends
(3 in 2020 and 29 in 2021), and 54 rows with `recovery_percentage = 0`. These
zeros are consistent with service outages or reporting gaps rather than
measured zero demand. Of the 54 zero-percentage rows, 22 still have between 2
and 22 trips, which is consistent with integer rounding. The zeros are retained
as published; do not impute them. Exclude or flag them explicitly in ratios,
log-transformed models, or any analysis where a zero denominator matters.

## Running the notebook

Prerequisites used for the validated run:

- Python 3.13.5
- pandas 2.3.3, NumPy 2.3.1, Matplotlib 3.11.2, Seaborn 0.13.2
- Jupyter (the `python3` kernel)

From the repository root (the folder containing `WEEK ONE`):

```bash
jupyter nbconvert --to notebook --execute --inplace "WEEK ONE/python/MTA_Processing.ipynb"
```

Or open the notebook in JupyterLab/VS Code and choose **Run All**. The notebook
is written to run top to bottom in a fresh kernel.

The notebook locates the project root by walking up from the current working
directory until it finds `WEEK ONE/python` and `WEEK ONE/database`. It then:

1. reads `WEEK ONE/data/raw/MTA_Daily_Ridership.csv`;
2. writes `WEEK ONE/MTA_Daily_Ridership_Cleaned.csv`;
3. writes `WEEK ONE/database/dim_date.csv`,
   `WEEK ONE/database/dim_transportation.csv`, and
   `WEEK ONE/database/fact_daily_metrics.csv`.

Output directories are created automatically. Two environment variables can
override the defaults:

- `MTA_PROJECT_ROOT`: path to the folder containing `WEEK ONE` (useful when the
  notebook is launched from outside the project).
- `MTA_SOURCE_DATA_PATH`: path to a different copy of the original CSV.

## Running the SQL

Create a database, build the schema, and load the CSVs. Run both commands from
the repository root; `load.sql` uses psql's client-side `\copy`, so its relative
paths are resolved from the current shell directory.

```bash
createdb mta_ridership
psql -d mta_ridership -f "WEEK ONE/sql/tables and relationships.sql"
psql -d mta_ridership -f "WEEK ONE/sql/load.sql"
```

On Windows, use the full path to `psql.exe` if it is not on `PATH`, for example:

```powershell
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" -d mta_ridership -f "WEEK ONE/sql/tables and relationships.sql"
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" -d mta_ridership -f "WEEK ONE/sql/load.sql"
```

`tables and relationships.sql` rebuilds the three tables by dropping and
recreating them, so do not run it against a database whose Week 1 data you need
to keep. `load.sql` truncates and reloads the three tables inside one
transaction. If a `COPY` or validation check fails, the transaction rolls back
and the previous contents remain.

The load checks row counts (1,706 / 7 / 11,942), the number of distinct dates
and systems, duplicate fact grains, foreign-key coverage, non-negative
measures, and exactly 1,706 fact rows per system. The primary key, `NOT NULL`,
`CHECK`, and foreign-key constraints also reject duplicate facts, null foreign
keys, negative measures, and orphan keys.

Quick verification:

```sql
SELECT count(*) FROM dim_date;              -- 1706
SELECT count(*) FROM dim_transportation;    -- 7
SELECT count(*) FROM fact_daily_metrics;    -- 11942
```

## Validation summary

The Week 1 checks that were executed against the files and an isolated
PostgreSQL database:

- Original and cleaned CSVs are identical: 1,706 rows × 15 columns, 0 missing
  values, 0 duplicate rows, 0 duplicate dates, 0 negative values, and a complete
  daily range from 2020-03-01 to 2024-10-31.
- `dim_date` has 1,706 rows, `dim_transportation` has 7 rows, and
  `fact_daily_metrics` has 11,942 rows.
- No duplicate `(date_key, transport_id)` pairs and no foreign-key violations.
- All 14 original measures reconstruct exactly from the fact table.
- PostgreSQL rejects duplicate fact grains, null foreign keys, negative
  `activity_value`, and negative `recovery_percentage`; all rejection tests were
  rolled back.
